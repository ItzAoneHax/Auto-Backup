# Auto-Backup 设计方案

> 基于百度网盘开放平台的 Linux 服务器自动备份工具（Java 17）
>
> 官方接口文档: https://pan.baidu.com/union/doc/

## 1. 背景与目标

在一台 Linux 服务器上, 将指定目录定期备份到百度网盘, 并满足以下要求:

| 要求 | 实现 |
| --- | --- |
| 自动备份 | 常驻进程每天在配置时间自动打包上传, 无需人工干预 |
| 清理过期 | 云端 `daily/` 目录只保留近 N 天(默认 3 天)的日期文件夹, 到期整夹自动删除 |
| 日期与服务器分目录 | 每天一个 `daily/<yyyy-MM-dd>/` 日期文件夹, 其中每个备份源(服务器)单独一个以源目录名命名的子文件夹 |
| 每天自动备份(至多留存近 3 天) | 每日 `backup.dailyTime` 触发; 保留天数由 `backup.retainDays` 控制 |
| 每月/每年永久备份 | 每月/每年第一次成功备份后, 云端复制一份到 `monthly/<yyyy-MM>/<服务器名>/`、`yearly/<yyyy>/<服务器名>/`, 永不清理 |
| 快照自动补全 | 每轮收尾核对 daily 与 monthly/yearly 的对象集合, 缺失的(月中新加的备份源、复制中断/失败)从 daily 云端复制补全, 同月已留档批次不重复 |
| 每次备份生成一并上传的日志 | 每次运行生成 `backup-<日期时间>.log`, 备份结束后上传到当日日期文件夹根部同期留存 |
| 方便自定义配置项 | 全部选项集中在 `config/application.properties`, 模板带中文注释 |

## 2. 技术选型

| 项目 | 选择 | 理由 |
| --- | --- | --- |
| 语言/运行时 | Java 17+ | 跨平台、服务器常见; record/switch 等语法简洁 |
| 构建 | Maven + shade | 打成单个可执行 fat jar, 部署只需一个文件 + JRE |
| HTTP | JDK 内置 `java.net.http.HttpClient` | 零依赖, 支持 URL 编码表单与 multipart |
| JSON | Jackson | 解析网盘接口响应、构造请求参数 |
| 打包 | Apache Commons Compress | 生成 tar.gz(标准格式, 服务器上可直接 `tar -xzf` 解开) |
| 调度 | 进程内定时器 | 免 crontab, systemd 一个服务搞定; 也支持外部 cron 调 `run` |

依赖总数 2 个(不含测试), 没有框架、没有数据库、没有 Web 服务。

## 4. 备份流程(单次运行)

1. **准备**: 校验配置 → 加载/刷新令牌 → 创建本地 work/logs 目录 → 远程建当日日期文件夹 `daily/<yyyy-MM-dd>/`(`mkdir -p` 语义, 幂等)。
2. **逐源打包**: 每个 `backup.sources` 目录打包为 `{目录名}-{yyyy-MM-dd_HHmmss}.tar.gz`, 归档内以目录名为根; 支持 glob 排除规则; 符号链接与无权限文件跳过并记警告。
3. **分片上传**(见第 5 节)到 `daily/<yyyy-MM-dd>/<服务器名>/`(服务器名即源目录目录名)。
4. **月度/年度留档**: 若 `monthly/<yyyy-MM>/<服务器名>/`、`yearly/<yyyy>/<服务器名>/` 缺少本批文件, 则把本次上传的 daily 文件在云端复制一份过去(服务端复制, 无二次上传流量; 复制失败时回退从本地上传)。快照目录已有**其他批次**(文件名时间戳不同)即视为本期间已完成, 不重复留档; 若目录里只有本批的一部分(上次复制中断), 只补齐缺失的分卷。
5. **快照补全核对**: 全部备份源处理完后, 对本轮成功上传的每个源再核对一遍 monthly/yearly, 仍缺失时(月中新加的备份源、快照复制反复失败)从 daily 云端复制补全; 失败只告警, 留待下次运行重试。
6. **本地清理**: 默认删除本地归档(`backup.deleteLocalArchive` 可关)。
7. **云端过期清理**: 见第 6 节。
8. **日志上传**: 本地日志写完关闭后上传到 `daily/<yyyy-MM-dd>/` 根部, 文件名内嵌日期, 随所在日期文件夹同期被清理。

单个备份源失败只记错误, 不影响其他源; 任一环节失败则本次运行整体记为失败(`run` 命令退出码 1, 方便外部监控告警)。

## 5. 分片上传(官方三步流程)

```
本地文件 ──▶ ① 计算 4MB(可配) 分片 md5 列表
        ──▶ ② precreate 预上传, 获得 uploadid 与待传分片序号
                └─ 若云端已有相同内容 → 秒传, 直接完成
        ──▶ ③ locateupload 动态获取上传域名(servers 中任一 https 域名, 缓存约 60 秒)
        ──▶ ④ 逐片 superfile2 上传(每片独立重试, 指数退避, 校验服务端 md5)
        ──▶ ⑤ create 合并分片, 返回 fs_id
```

- 同名远程文件 `rtype=3` 覆盖(precreate 与 create 保持一致), 重复运行不会堆积副本。
- 预上传返回的 `block_list` 为空数组时等价于 `[0]`, 仍需上传第 0 片(官方文档规定)。
- 分片/单文件上限与账号等级挂钩: 普通用户 4MB/4GB, 会员 16MB/10GB, 超级会员 32MB/20GB。
- 令牌错误码(-6/20016/20017/31045, 见官方公共错误码表)在分片层不重试, 上层刷新令牌后整体重来一次; 111 为异步任务冲突, 非令牌错误。

## 6. 保留策略

云端目录布局(daily 按日期文件夹分天, 其下按服务器名分目录; 服务器名 = 备份源目录的目录名):

```
{pan.remoteDir}
├── daily/                                      # 每日备份 + 日志, 滚动清理
│   ├── 2026-08-22/
│   │   └── myserver/
│   │       └── myserver-2026-08-22_030000.tar.gz
│   └── 2026-08-23/                             # 一天一个日期文件夹
│       ├── myserver/
│       │   └── myserver-2026-08-23_030000.tar.gz
│       ├── mysql_data/                         # 第二个备份源单独一个子文件夹
│       │   └── mysql_data-2026-08-23_030000.tar.gz
│       └── backup-2026-08-23_030000.log        # 运行日志放日期文件夹根部, 同期清理
├── monthly/                                    # 每月一份, 永久保留
│   └── 2026-08/
│       └── myserver/
│           └── myserver-2026-08-01_030000.tar.gz
└── yearly/                                     # 每年一份, 永久保留
    └── 2026/
        └── myserver/
            └── myserver-2026-01-01_030000.tar.gz
```

清理规则(每天备份成功后执行一次):

| 规则 | 说明 |
| --- | --- |
| 清理范围 | 仅 `daily/` 目录, `monthly/` 与 `yearly/` 永不清理 |
| 新结构判定 | 子目录名严格为 `yyyy-MM-dd` 即视为本程序生成的日期文件夹, 早于期限的**整夹删除** |
| 兼容旧结构 | v1.1 及更早的扁平文件按文件名内嵌 `yyyy-MM-dd` 日期逐个删除 |
| 保留条件 | 日期 >= 今天 - (retainDays - 1); 默认 3 天即今天、昨天、前天 |
| 安全阀 | 名字解析不出日期的文件与目录一律不动(手动放的内容不受影响) |
| 本地日志 | 同理, 按 `backup.logRetainDays`(默认 30 天)清理 |

## 7. 认证与令牌管理

采用官方 **OAuth2.0 设备码模式**(服务器无浏览器也能授权):

1. `login` 命令向百度申请设备码, 打印验证地址 + 验证码(或扫码);
2. 用户在任意设备完成授权, 程序轮询拿到 `access_token`(30 天)与 `refresh_token`(10 年);
3. 凭证存 `config/token.json`(Linux 下权限 600), 已加入 `.gitignore`;
4. 此后每次运行前, 距过期不足 7 天自动用 refresh_token 换新——只要程序每月至少成功运行一次, 用户永远不需要重新登录。

## 8. 可靠性设计

| 场景 | 处理 |
| --- | --- |
| 分片上传失败 | 每片独立重试(默认 3 次, 指数退避), 校验服务端返回 md5 |
| 令牌中途过期(官方错误码 -6/20016/20017/31045) | 刷新后整体重试一次 |
| 删除时撞上异步任务冲突(errno 111) | 等待 5 秒自动重试一次(官方建议) |
| 服务器停机错过备份时间 | 守护进程启动后发现当天已过点且未运行 → 立即补跑 |
| 当天重复触发 | `work/state.properties` 记录最近运行日期, 同日不重复 |
| 双实例冲突(手动 run 撞上 daemon) | 文件锁 `work/auto-backup.lock` |
| 单个源失败 | 记错误继续下一个源, 整体退出码 1 |
| 上传后进程崩溃前清理 | 同名覆盖 + 幂等流程, 重跑即可收敛 |
| systemd 意外退出 | `Restart=on-failure` 自动拉起 |

## 9. 安全设计

- `config/application.properties`(含 AppKey/SecretKey)与 `config/token.json` 均在 `.gitignore` 中, 仓库只提交 `.example` 模板;
- 日志中 SecretKey 打码显示;
- token 文件在 Linux 下自动 chmod 600;
- 传输全程 HTTPS。

## 10. 已知限制

- 单文件上限与账号等级挂钩(官方规则): 普通用户分片固定 4MB、单文件 4GB; 会员 16MB、10GB; 超级会员 32MB、20GB。普通用户请保持 `upload.chunkSizeMB=4`;
- 官方接口不支持空文件上传(本程序的归档与日志文件始终非空, 不受影响);
- 个人应用只能访问自己的应用目录 `/apps/{应用目录名}`, 这是平台限制;
- 官方对频控的具体数值未公开("仅对异常行为限制", 上传每日 10 万次上限);
- 备份为整包归档(非增量), 适合中小规模数据(建议 < 几 GB)。

## 11. 后续可扩展方向

- 备份失败通知(邮件/Server酱/Telegram);
- 增量备份(基于文件 mtime 对比上次清单);
- 多账号/多网盘支持;
- 备份数据库专用模式(mysqldump 前置钩子);
- 上传前后自定义脚本钩子(`backup.preScript` / `backup.postScript`)。
